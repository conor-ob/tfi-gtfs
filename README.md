# tfi-gtfs

Departures and nearby stops for Dublin public transport, built on the NTA's static GTFS Schedule and GTFS-Realtime feed. Consumed by the owner's own apps over tRPC, and by a Departure Board at home over WebSocket.

Domain language lives in [CONTEXT.md](CONTEXT.md); architectural decisions in [docs/adr](docs/adr).

## Layout

Turborepo + pnpm monorepo, TypeScript throughout, hexagonal architecture.

| Path | Role |
|---|---|
| `apps/server` | Fastify server, composition root, tRPC at `/trpc`, Departure Board WebSocket at `/departure-board`. Serves the Schedule file from the Schedule store, hot-swapping new ones (`ScheduleLoader`) |
| `apps/web` | React + Tailwind pages of live Departures at the Watched Stops (`/` merged, `/stops` per Stop), served by Caddy |
| `apps/dartboard` | Full-screen LED board of live Departures at the Watched Stops, made to look like the Departure Board, served by Caddy |
| `jobs/schedule-sync` | Daily Railway cron: Schedule Import (own composition root). Builds the whole Schedule as a SQLite file and publishes it to the Schedule store (ADR 0011) |
| `packages/tfi-gtfs-core` | Domain, services, inbound/outbound ports. No I/O |
| `packages/tfi-gtfs-db` | Drizzle schema + migrations and the read repositories. Nothing uses it any more; it goes with Postgres |
| `packages/tfi-gtfs-sqlite` | The Schedule as a `node:sqlite` file (ADR 0011): `schema.sql`, the import that builds it, and repositories over a swappable handle. The import is used by `schedule-sync`, the repositories by the server |
| `packages/tfi-gtfs-redis` | Redis adapter: `RedisTripUpdateStore` and the client factory |
| `packages/tfi-gtfs-schedule-store` | `ScheduleStore` adapters: `FsScheduleStore` (a local folder), `S3ScheduleStore` (the Railway bucket) and `createScheduleStore`, which picks one from the env. Used by `schedule-sync` and the server |
| `packages/tfi-gtfs-trpc` | tRPC router, thin layer over core services |
| `packages/tfi-gtfs-departure-board` | Departure Board adapter: Transit Tracker WebSocket messages, `routeStopPairs` parser, Departures to trips |
| `packages/tfi-gtfs-web-shared` | Shared by the web apps: tRPC client, the Watched Stops and their Walk Times, `useStopDepartures`, `useNow` |
| `packages/tfi-gtfs-utils` | Shared helpers (env schemas, `assertNever`) |
| `packages/gtfs-static` | Adapter: remote zip → CSV streams (`openRemoteZip`) |
| `packages/gtfs-realtime` | Adapter: NTA GTFS-Realtime client + protobuf decoding |

## Local development

```sh
pnpm install
pnpm db:up        # Postgres 18 on localhost:5432 (db: tfi-gtfs, tests: tfi-gtfs-test) and Redis 8 on 6379 (tests: db 1), in Docker
pnpm dev
```

`tfi-gtfs-db` tests run against the `tfi-gtfs-test` database and `tfi-gtfs-redis` tests against Redis database 1, so `pnpm db:up` before `pnpm test`. `pnpm --filter @tfi-gtfs/schedule-sync dev` fills `jobs/schedule-sync/.schedule/` from the live feed; a second run skips.

Env vars live in a per-package `.env`; copy each `.env.example`. `NTA_API_KEY` goes in `apps/server/.env`, whose `SCHEDULE_DIR` points at `jobs/schedule-sync/.schedule/`, so `pnpm dev` serves what `schedule-sync` published there, with no Postgres; `/health` is 503 until it has opened a file. `apps/web` (port 5173) and `apps/dartboard` (port 5174) proxy `/api` to the local server; set `API_PROXY_TARGET=https://<web domain>/api` in their `.env` to use production instead. `pnpm db:reset` wipes the database volume and starts fresh. It uses the default ports 5432 and 6379, so stop any other local Postgres or Redis first. The server keeps Trip Updates in memory unless `TRIP_UPDATE_STORE=redis` (with `REDIS_URL`) is set in `apps/server/.env`.

## Design notes

Smaller decisions that don't warrant an ADR:

- **Feed URLs**: Schedule `https://www.transportforireland.ie/transitData/Data/GTFS_Realtime.zip`; Realtime `https://api.nationaltransport.ie/gtfsr/v2/TripUpdates` with an `x-api-key` header.
- **Import filtering**: every Agency and every Stop is kept (ADRs 0008 and 0011). Routes and Trips are held in memory until `stop_times` has streamed, so only Trips with a Stop Time are written, then their Routes, Agencies and Service Calendars, and the Stops they serve plus their parent Stations.
- **Watched Stops**: the Stops the apps and the Departure Board show (`stops.ts` in `tfi-gtfs-web-shared`, and each board's schedule string). They no longer filter the Schedule Import (ADR 0011, superseding 0007).
- **Entries imported**: agency, routes, trips, stops, calendar, calendar_dates, stop_times, feed_info. `shapes.txt` (91 MB compressed) and `translations.txt` are skipped for now; keep `trips.shape_id` so shapes can be added later as one more table.
- **Change detection**: skip the import when the zip's ETag and `feed_info.feed_version` match the Schedule store's `latest.json` for the current schema version. `public.schedule_import` is no longer written.
- **Times**: store Stop Times as integer seconds since the start of the Service Day (GTFS times can exceed `24:00:00`). Service Days are in `Europe/Dublin`. "Next Departures" must check active Service Calendars for both today and yesterday.
- **Departures**: `departures.getByStop({ stopId, from?, walkTimeSeconds?, directionId?, limit? })` looks 24 hours ahead across yesterday's, today's and tomorrow's Service Days, then merges them. `walkTimeSeconds` (the Walk Time) starts from now plus that many seconds instead of `from`; the Departure Board passes its own the same way. `directionId` (0 or 1) filters Trips in SQL, so the limit is filled from that direction alone. A Service Day starts at noon minus 12 hours (GTFS), which differs from midnight on the two days the clocks change. Stop Times with `pickup_type = 1` (every Trip's last Stop) are not Departures. Today's feed has no parent Stations, so a Stop's Departures don't include its platforms yet.
- **Route colours**: the NTA Schedule has no `route_color` / `route_text_color`, so `withRouteColors` in core fills them per Agency (Irish Rail `IR` green, Go-Ahead Ireland `3` blue, Dublin Bus `1` yellow) on every Departure when the feed's are empty. It runs at read time, not in the Schedule Import, so a change lands without waiting for a new Feed Version and the `gtfs` tables stay the publisher's. The feed's own colours win if the NTA ever publishes them. The web page and the Departure Board both take their colours from the Departure.
- **Nearby stops**: every Stop in the Schedule, with no PostGIS. `stops.getNearby({ lat, lon, radius?, limit? })` (radius in metres, default 500, max 2000) filters on a bounding box over the indexed `stop_lat`/`stop_lon`, then trims and sorts by haversine distance in SQL, behind a `findStopsNear` port. Only Stops you can board at (`location_type` 0 or empty) are returned, since a Station has no Departures of its own yet.
- **Server cache invalidation**: the pointer is the signal. `ScheduleLoader` reads `latest.json` for `SCHEDULE_SCHEMA_VERSION` at startup and every `SCHEDULE_POLL_INTERVAL_SECONDS` (default 300), never hearing from the job directly. When the key or hash changes, it gunzips the object through `fetchSchedule`'s hash check to `<feedVersion>.sqlite.partial` in a temp folder, renames it, opens it read-only, swaps it into the `ScheduleDatabase` (dropping cached statements), then closes and deletes the old file, logging the Feed Version. A failed poll or hash mismatch is logged and the current file keeps serving. Refreshes run one at a time. `/health` is 503 until a file is open.
- **Realtime overlay**: match Trip Updates to Departures on `trip_id` + `start_date`; apply each Stop Time Update's Delay, and carry the last Delay forward to later Stops, falling back to the Trip Update's own Delay before the first one. Ignore ADDED trips for now. CANCELED trips and SKIPPED stops remove the Departure. `departures.getByStop` always queries the hour before for late Trips (it only knows which Trip Updates to ask for afterwards) and keeps those Departures only when there are Trip Updates; it orders and filters by Predicted Departure where there is one.
- **Realtime refresh**: no poller (ADR 0009). Each Departures request asks the `TripUpdateStore` for just its Trips' Trip Updates and tries to claim a 60-second cooldown (`REALTIME_REFRESH_INTERVAL_SECONDS`; the NTA doesn't publish its rate limit). Whoever claims it reads the Realtime Feed in the background. A request with no Trip Updates at all waits up to 2 s for a read under way in the same process, whoever claimed it, since the web page asks for every Stop in one batch. A snapshot expires 5 minutes after the feed's timestamp. `TRIP_UPDATE_STORE` picks `memory` (default, one replica) or `redis` (production). Redis commands time out after 500 ms and don't queue while disconnected, and any store error means Scheduled Departures only. Decoded protobuf messages return defaults (`0`) for missing fields, so the adapter checks a field is present before reading a Delay.
- **Schedule store**: the seam for ADR 0011. `schedule-sync` publishes through it; the server reads it. `publishSchedule` in core uploads `schedule/v<schemaVersion>/<feedVersion>.sqlite.gz` while hashing it, writes `latest.json` last, then deletes all but the newest seven files (by last-modified) of that schema version, never the one just published. `fetchSchedule` follows the pointer and streams the object through a sha256 check that throws `ScheduleHashMismatchError` at the end, so the caller must read it through (to a temp file) before using it. The pointer's `etag` is the Schedule zip's, for change detection. `SCHEDULE_STORE=fs|s3` (default `fs`) and `SCHEDULE_DIR` (default `.schedule/`, relative to the working directory, gitignored) come from `scheduleStoreEnvSchema` in `tfi-gtfs-utils`; with `s3`, `SCHEDULE_BUCKET_ENDPOINT`, `SCHEDULE_BUCKET_REGION`, `SCHEDULE_BUCKET_NAME`, `SCHEDULE_BUCKET_ACCESS_KEY_ID` and `SCHEDULE_BUCKET_SECRET_ACCESS_KEY` are each required. `S3ScheduleStore` uploads through `@aws-sdk/lib-storage`, so a stream of unknown length goes multipart when it's large.
- **Cron**: `schedule-sync` at `0 3 * * *` (Railway cron is UTC, so 03:00 Irish winter time and 04:00 summer time; the Schedule is published around 22:30 UTC).
- **SQLite Schedule file**: `tfi-gtfs-sqlite` loads rows into GTFS-shaped `staging_*` text tables in the file being built, adds their keys and runs the same checks as the Postgres import, then runs `schema.sql`, derives the integer-ID tables, drops the text tables, `ANALYZE`s and `VACUUM`s, and renames `<path>.staging` to `<path>`, which `build()` hands back as a `BuiltSchedule`. `schedule-sync` builds in a temp folder it removes afterwards, and `ScheduleImportService` gzips the file while publishing it, logging the Feed Version, the key and both sizes. It builds with `journal_mode = OFF`, `synchronous = OFF` and `temp_store = FILE` (memory temp storage cost about 190 MB more RSS). An exclusive lock on the staging file stops two imports overlapping, and is released if the process dies. Stop Times without a `departure_time` are left out of `stop_times`. `schema.sql` sets `PRAGMA user_version`, which must equal `SCHEDULE_SCHEMA_VERSION`; the file's `schedule_import` row holds its Feed Version and ETag. `schema.sql` is read from beside `schema.ts` at runtime, so a tsdown bundle must copy it next to its output (`schedule-sync`'s `tsdown.config.ts` does). Repositories prepare plain SQL through `ScheduleDatabase`, which caches statements per handle and drops them on `swap()`.
- **Builds**: workspace packages export TypeScript source and are never built on their own. The server and `schedule-sync` are bundled with tsdown, which inlines `@tfi-gtfs/*` packages and their dependencies and leaves only each app's own npm dependencies external (the Docker images delete `src/`). `tsc` is only used for typechecking; in development the server runs with `tsx watch`.
- **Deploy**: `.railway/railway.ts` declares the server, Postgres with its 5 GB `postgres-volume` (Railway provisions it with the database; declaring it adopts it so resizes go through IaC) the `web` service (its domain is added in the dashboard), and the `schedule-sync` cron in `europe-west4`. It also declares a `redis` database for Trip Updates (no volume needed; they're disposable), and the `schedule` bucket in `ams` for the Schedule files. `schedule-sync` and the server get `SCHEDULE_STORE=s3` and the `SCHEDULE_BUCKET_*` variables through `ref(bucket, …)`, and no database variables. The server has no pre-deploy command, and its healthcheck waits for an open Schedule, so a new environment or schema version needs `schedule-sync` run by hand first. It stays at one replica for now. `NTA_API_KEY` is `preserve()`d: set it once in the Railway dashboard and seal it there. Only secrets are `preserve()`d; other variables are declared in `railway.ts`, because a dashboard edit while a `.railway/` PR is open moves the environment, the pinned plan is refused on merge, and the failed check holds back that commit's deploy. `ORIGIN` is optional; CORS allows no browser origins unless it's set. Railway waits for a commit's GitHub checks before deploying it (`checkSuites`).
- **Web**: `apps/web` shows Departures for the stops hardcoded in `stops.ts` in `tfi-gtfs-web-shared` (any Stop in the Schedule works) on two pages, picked by path with no router (Caddy's `try_files` serves `index.html` for each). `/stops` has a section per stop. `/` (and any other path) merges them into one list, soonest first, like the Departure Board: each stop has a Walk Time, passed as `walkTimeSeconds` so the query stays the same between refetches, and the page filters by it again on every tick, so a Departure goes once it can't be caught. `apps/dartboard` draws every Stop's Departures from now full screen, ignoring Walk Times so it can be checked on the way (`useStopDepartures` serves both apps), on a canvas made to look like the Departure Board, but in a section per Stop under an amber header: 128 round LEDs across, as many tall as the screen's shape allows, and as many rows as fit, shared equally between the Stops (at least one each, at most 50), kept inside the safe area while unlit LEDs carry on to the screen's edges, a 5×7 pixel font (`led-font.ts`; accents are stripped, unknown characters drawn as `?`), Route names in their colour, a blinking signal icon on live Departures, a shimmer over placeholder rows while loading, and a colour wipe on start-up (skipped with reduced motion). Added to an iPhone Home Screen it opens full screen as "DARTboard", with `public/apple-touch-icon.png` as its icon; the tags iOS reads are in its `index.html`. Both refetch every 30 seconds, so Trip Updates are refreshed about once a minute while a page is open. Each is its own Railway service whose Caddy serves the build and proxies `/api/*` to the server over Railway private networking, so the browser never calls the server directly (each domain is added in the dashboard). The pages are public, with no auth.
- **Departure Board**: an Adafruit Matrix Portal S3 with two Waveshare RGB-Matrix-P2.5-64x32 panels (about €67), on a 5 V USB-C supply, in a 3D-printed case with 12 M3×8 screws. It runs the stock Transit Tracker firmware, flashed from its web installer, and the server speaks its WebSocket protocol at `/departure-board` (ADR 0010), reached through Caddy at `wss://<web domain>/api/departure-board`. The board's settings are ESPHome entities you set on the LAN (`curl -X POST 'http://<board ip>/text/base_url_config/set?value=<url-encoded>'`, and the same for `schedule_config`). List mode is `sequential` (the firmware's default; `curl -X POST 'http://<board ip>/select/list_mode_config/set?option=sequential'`), so the board shows the soonest Departures across every pair, and a Stop with none of them isn't shown. `nextPerRoute` would instead show one row per Stop, Route and direction. The schedule string is `route,stop,offset` pairs joined by `;`: `*` for any Route, `:0`/`:1` for a direction, and a negative offset in seconds for the Walk Time. For example, `*:0,8250IR0014,-300;*,8250DB003062,-240` means DART northbound at Dalkey with a 5-minute walk, plus every bus at Breffni Road with a 4-minute walk. The value is limited to 255 characters; any Stop in the Schedule works. Caddy's `reverse_proxy` passes the WebSocket upgrade through unchanged, and the rate limit counts only the upgrade request, so an open board isn't throttled. Each board's socket reads up to 50 Departures per pair every 30 s; one that can't be read skips that push but keeps heartbeats going.
- **CI**: `ci.yaml` is one job against Postgres 18 and Redis 8 services: biome, typecheck, build, migration checks (journal, no ungenerated changes, `pnpm db:migrate` in `tfi-gtfs-db` applies to an empty database and re-applies as a no-op), then tests. `railway-plan.yaml` plans PRs that touch `.railway/` and comments the diff; `railway-apply.yaml` applies that pinned plan on merge, so there's no manual trigger (use `railway config apply` locally after a dashboard change). Both use the `RAILWAY_TOKEN` project token secret.

## Roadmap

1. ~~**Schedule tables**~~: done. `gtfs` schema plus `public.schedule_import` for change detection; no foreign keys (see `tfi-gtfs-db` schema comment).
2. ~~**Schedule Import**~~: done. `pnpm --filter @tfi-gtfs/schedule-sync dev` builds the live feed into a SQLite file and publishes it to `.schedule/` (about 40 s, 530 MB peak RSS, 8.0M Stop Times; a 176 MB file, 38 MB gzipped).
3. ~~**Departures (scheduled)**~~: done. `DepartureService` in core, `DepartureRepositoryImpl` in db, `departures.getByStop` over tRPC.
4. ~~**Nearby stops**~~: done. `StopService` in core, `StopRepositoryImpl` in db, `stops.getNearby` over tRPC.
5. ~~**Realtime**~~: done. `NtaRealtimeFeedClient` in `gtfs-realtime`, `InMemoryTripUpdateStore` behind a `TripUpdateStore` port, `RealtimeService` on-demand poller (ADR 0005, since replaced by 0009), `predictedDeparture` on each Departure.
6. ~~**Deploy**~~: done. `.railway/railway.ts` with server, Postgres and the `schedule-sync` cron; `railway config plan` / `apply` from a linked checkout.
7. ~~**CI**~~: done. `ci.yaml`, `railway-plan.yaml` and `railway-apply.yaml` under `.github/workflows`.
8. ~~**Watched Stops**~~: done, then reverted. The Schedule Import kept only the Watched Stops (ADR 0007) until ADR 0011.
9. ~~**Web**~~: done. `apps/web`, a single page of live Departures at the Watched Stops.
10. ~~**Realtime in Redis**~~: done. `RedisTripUpdateStore` in `tfi-gtfs-redis`, refreshed on read instead of polled (ADR 0009).
11. ~~**Departure Board**~~: done. `tfi-gtfs-departure-board` inbound adapter and the `/departure-board` WebSocket route, speaking the Transit Tracker protocol (ADR 0010).

## Spikes

- `pnpm --filter @tfi-gtfs/gtfs-static spike [--slow]`: streams the whole Schedule zip and reports entry order, row counts per Agency, timing and peak memory.
- `pnpm --filter @tfi-gtfs/gtfs-realtime spike`: one TripUpdates request; reports feed shape and how Trip Updates join to static `trip_id`s.
