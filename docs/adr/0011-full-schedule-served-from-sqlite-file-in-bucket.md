# Serve the full Schedule from a SQLite file in a Railway bucket

Supersedes [0007](0007-import-only-watched-stops.md) and [0006](0006-schedule-served-from-sqlite-file.md), and with them [0003](0003-schedule-import-schema-swap.md) and the "writes directly to Postgres" half of [0002](0002-schedule-import-job-writes-directly-to-postgres.md).

0007 kept Postgres and imported only Watched Stops. That fixed Postgres's memory, but only by giving up most of the Schedule: Nearby Stops and Departures cover about ten Stops, and the Departure Board can only ask for those. Putting every Stop back into Postgres is what used to push it to nearly 2 GB for hours after each import. So the Schedule Import now keeps every Stop again, and builds one SQLite file per Feed Version, which it publishes to a Railway Storage Bucket. The server downloads that file and queries it in-process with `node:sqlite`. Postgres is removed, and Drizzle goes with it.

This is 0006's design, revised:

- **Job**: `schedule-sync` stays a separate daily cron (the rest of 0002 holds). It runs `ScheduleImportService` against a `node:sqlite` `ScheduleImportRepository` on local disk, with no Watched Stops filter. It gzips the file and uploads it as `schedule/v<schemaVersion>/<feedVersion>.sqlite.gz`. Then it overwrites `schedule/v<schemaVersion>/latest.json` with `{ key, feedVersion, etag, sha256, importedAt }`. Writing the pointer last is the publish step: readers never see a half-uploaded file, and a failed import leaves the pointer alone. The pointer's `etag` and `feedVersion` replace `public.schedule_import` for change detection. The job keeps the last seven files per schema version and deletes older ones.
- **Server**: on startup, and then every 5 minutes (`SCHEDULE_POLL_INTERVAL_SECONDS`), the server reads the pointer for the schema version its code expects. The job never signals the server. When the pointer changes, the server downloads the file to its ephemeral disk, checks the hash, opens it read-only and swaps the handle behind the repositories, then deletes the previous file. `node:sqlite` is synchronous, so no query is in flight across the swap. An object whose hash doesn't match is rejected, and the current file keeps serving. The server needs no volume.
- **Health**: `/health` reports healthy only once a Schedule is open, so a deploy never serves an empty server. The `preDeploy` migrate command goes, since there are no migrations.
- **Layout**: integer IDs for Trips, Stops, Routes and Services. `stop_times` is a `WITHOUT ROWID` table keyed on `(stop, departure_time, trip, stop_sequence)`, holding only the columns Departures read. GTFS IDs stay as unique text columns on their own tables. The job may load into GTFS-shaped text tables and derive this layout from them; integrity checks run on the text tables.
- **Schema and queries**: the file's schema is one hand-written `.sql` file, the single source of truth. The job runs it to create the file, and the test fixture builder runs it too. Repositories prepare plain SQL on the current `DatabaseSync` handle. Prepared statements are cached per handle and dropped on a swap. Each repository declares its row type and casts to it.
- **Schema versions**: the schema version is part of the bucket path, and it changes whenever the `.sql` file's layout does. A deploy that changes the layout can ship before the job writes files in the new layout, and an older server keeps reading the layout it understands.
- **Storage**: `bucket("schedule", { region: "ams" })` in `.railway/railway.ts`, next to `europe-west4`. Services get their credentials through `ref(bucket, "ENDPOINT" | "REGION" | "BUCKET" | "ACCESS_KEY_ID" | "SECRET_ACCESS_KEY")`, so nothing needs `preserve()`. The bucket is S3-compatible (Tigris) and public-network only. It has no versioning or lifecycle rules, which is why pruning and rollback live in code. Tigris guarantees read-after-write within a region, overwrites included, so a reader of `latest.json` sees the new pointer.
- **Local and CI**: the job and server reach the bucket through a `ScheduleStore` seam (get pointer, get object, put, list, delete). It has two adapters: `S3ScheduleStore`, and `FsScheduleStore`, a local folder with the bucket's key layout. `SCHEDULE_STORE=fs|s3` picks one, like `TRIP_UPDATE_STORE`. It defaults to `fs`, in a gitignored `.schedule/` (`SCHEDULE_DIR`). `railway.ts` sets `s3`, and with `s3`, missing bucket variables fail at startup. `FsScheduleStore` writes `latest.json` to a temp file and renames it into place. It uses the file's sha256 in place of an ETag. Locally, `schedule-sync` fills the folder from the live feed.

## Considered Options

- **Keep Postgres with Watched Stops (0007)**: this works today and costs about $0.70 a month. It is rejected because it gives up the full Schedule, and because it keeps a stateful service to run, migrate and back up. This change is not justified on cost.
- **Keep every Stop in Postgres**: this is what reached nearly 2 GB of memory after an import, and the memory took hours to come down. Railway counts the page cache as used memory.
- **Drizzle over the SQLite file**: it matches raw SQL row for row and survives the hot swap, but it would serve only about four reads once Postgres is gone. Drizzle 0.45 has no `node:sqlite` driver (it needs `sqlite-proxy`), and it can't express `WITHOUT ROWID`. Its 1.0 drivers bind the client, which makes the swap harder. The fixture-file repository tests cover what its types would.
- **better-sqlite3 or libsql**: better-sqlite3 13 is the fallback if `node:sqlite` falls short. It is a native module, so it needs `neverBundle` in tsdown and a direct dependency in each app. libsql's native binaries are optional dependencies, which `pnpm prune --no-optional` removes. It also has no read-only mode, and its client is an async pool.
- **An S3 container for local development and CI**: MinIO's repository is archived, and the other S3 containers would only imitate S3. A folder behind the same seam tests the publish and read rules directly.
- **Redis, importing inside the server, baking the file into the image**: rejected in 0006 for reasons that still hold. Redis would hold the whole Schedule in RAM. Importing inside the server competes with requests, and a volume attaches to only one service. Baking the file into the image means a full redeploy every day.

## Consequences

- Measured against the full Schedule (Feed Version `64212183-…`) on Node 26, rerunning the 0006 spikes:
  - The integer-ID file is 160 MB, or 34.5 MB gzipped (it was 113 MB and 26 MB at 0006). `stop_times` is 145 MB of that.
  - The job peaks at 541 MB RSS. It runs for a couple of minutes a day, so this barely shows on the bill.
  - Departures at the busiest Stop (8,401 Stop Times) take 0.18 ms at p50 and 0.22 ms at p99. Departures at all 10,261 Stops take about 0.08 ms each, and Nearby Stops take 0.12 ms at p50.
  - The startup download takes about 0.3 s locally. During it, event-loop delay peaks at 1.6 ms.
  - A hot swap under a query loop gives 0 errors, and the slowest query is 0.4 ms.
  - RSS settles at about 121 MB with the whole file read. On Linux, the page cache over the file can add up to about 160 MB more. That cache is reclaimable, but Railway counts it as memory, so check Railway's memory graph after the first deploy.
- Every Stop is in the Schedule again. Nearby Stops searches all of them, and Departures and the Departure Board's schedule string can name any Stop. `WATCHED_STOP_IDS` goes. Watched Stops remain only as the Stops the apps and the Departure Board show.
- A deploy that bumps the schema version fails its healthcheck until someone runs `schedule-sync` by hand, because no file exists yet at the new path. Railway keeps the old deployment serving meanwhile. So the procedure is: merge, run the job, and redeploy the server if its healthcheck timed out. A new environment needs the same first run.
- Drizzle, `drizzle-kit`, the migrations and the CI migration checks leave the repo. Repository tests run against a file built from a fixture feed with the `.sql` schema. The publish and read rules (pointer last, hash check, keep seven, hot swap) are tested against `FsScheduleStore` in a temp folder. `S3ScheduleStore` is tested against a mocked S3 client, so nothing calls Tigris from CI, and the first deploy is that adapter's real integration test. CI and local development keep only Redis.
- Rollback means pointing `latest.json` at one of the seven older keys.
- Bucket storage is $0.015 per GB-month, rounded up to whole GB-months. API operations and downloads are free. The job's uploads are billed as egress at $0.05/GB, about $0.04 a month.
- Nothing durable is left in a database. If user-owned data arrives, it needs a home of its own, and it must not reference Schedule IDs in a way that breaks when the Schedule is replaced.
- 0004 (streaming zip entries), 0009 (Trip Updates in Redis) and 0010 (Departure Board) are unaffected, apart from 0010's warning for unwatched Stops. The server stays at one replica.
